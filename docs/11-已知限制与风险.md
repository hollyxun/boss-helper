# 11 · 已知限制与风险

本文分为四部分：

1. 产品/合规风险
2. 功能边界
3. 代码层面的已知问题
4. 维护与改进建议

> 说明：第 3 节是**基于当前源码的静态分析**。有些问题在当前版本可能被默认配置掩盖，或依赖目标站点/接口的实际行为；上线前应以真实环境验证为准。

## 1. 产品与合规风险

### 1.1 非官方工具

boss-helper-plus 不是 Boss 直聘官方产品，与平台没有合作关系。它通过页面注入、内部接口和 WebSocket 模拟用户操作，属于自动化工具。

### 1.2 账号风险

仓库根目录 `README.md` 已明确提示：

> 使用该脚本有一定风险（如黑号、封号、权重降低等），本项目不承担任何责任。

具体风险包括：

- 高频投递触发风控（“操作过于频繁”）
- 达到 120/150 次限制
- 自动化招呼语被判定为骚扰
- 账号被降权、限制沟通、封禁
- 接口/协议变更导致异常行为

### 1.3 使用条款

自动化操作可能违反目标网站的用户协议。项目声明“仅供学习交流，禁止用于商业用途”，但**这不能替代对平台条款的遵守**。

### 1.4 数据与隐私

- API Key 保存在扩展存储（默认 `sync:`），可能随浏览器账号同步
- `bst` Cookie 与 `window._PAGE.token` 被读取用于请求 Boss 接口
- AI Prompt 会把职位描述、公司、薪资、地址等发送给用户配置的第三方 AI 服务
- `net-conf.json` 请求会暴露 IP
- 扩展申请了 `http://*/*`、`https://*/*` 的广泛 host 权限

详见根目录 `PRIVACY.md` 与 [07-消息与通信.md](./07-消息与通信.md#8-隐私与安全)。

### 1.5 远程配置

`net-conf.json` 可以从远端下发：

- 版本提示
- Alert/Toast 公告
- 商店链接
- 反馈地址

这些内容会显示在扩展 UI 中。当前代码不会执行远端脚本，但远端链接可能把用户带到外部页面。使用时应确认来源可信。

## 2. 功能边界

| 边界               | 说明                                                                                                                       |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------- |
| **能收能回**       | 0.0.2 起 `AutoReplyService` 订阅 MQTT 的 `chat` 主题，可读取招聘方文字消息并用 AI 回复；聊天记录只在内存里作上下文，不落盘 |
| **自动回复有节制** | 同一岗位 8 秒内只回一次、最多 10 条；只处理文字消息，图片/卡片/语音忽略；只在本次页面会话投递过的岗位里匹配                |
| **无多账号**       | 已废弃，改为多配置预设；账号切换需用户自己处理                                                                             |
| **无服务端**       | 所有逻辑在浏览器；没有云端同步/任务队列                                                                                    |
| **无自动刷新**     | 页面无法滚动/没有新职位时需要用户手动操作                                                                                  |
| **依赖页面滚动**   | 翻页依赖页面自身懒加载/滚动，滚不到底就无法继续                                                                            |
| **投递上限**       | 默认 120，Boss 硬上限 150；达到后停止                                                                                      |
| **单页串行**       | 同一页面内逐职位处理，不并发                                                                                               |
| **不保证成功**     | 网络、风控、页面改版、AI 失败都会导致跳过                                                                                  |
| **无暗黑模式维护** | 建议使用 Dark Reader                                                                                                       |
| **无完整 i18n**    | 语言包只有扩展名/描述，UI 文案硬编码中文                                                                                   |
| **无自动化测试**   | 没有 test 脚本/测试目录                                                                                                    |

## 3. 代码层面的已知问题

### 3.1 相同公司/相同 HR 去重使用职位 id

**位置**：`src/composables/useApplying/handles.ts`

```ts
if (someSet.has(data.key)) return taskResult.skip('相同公司已投递')
...
someSet.set(data.key, Date.now())
```

`data.key` 来自 `JobData.key`，而转换逻辑是：

```ts
const key = `boss::${item.encryptJobId}`
```

问题：

- “相同公司”应该用 `encryptBrandId`
- “相同 HR”应该用 `encryptBossId`
- 现在两者都用 `encryptJobId`，同一职位不会重复出现，导致过滤器几乎不命中
- 两个存储键（`local:sameCompany`、`local:sameHr`）虽然分开，但内容语义相同

影响：跨岗位的公司/HR 去重没有实际效果。

### 3.2 好友状态过滤器没有数据来源

**位置**：`handles.ts` 的 `jobFriendStatus`

```ts
if (jobData.boss?.isFriend === true) return taskResult.skip('已经是好友了')
```

但 `convertBossZpJobItemToJobData` 里：

```ts
isFriend: false
```

详情补充时也没有更新 `isFriend`。`BossZpDetailData.relationInfo.beFriend` 是可用的字段，但未被使用。

影响：“好友过滤(已聊)”基本不会命中；“已沟通”过滤器（`rawData.jobitem.contact`）承担了实际去重。

### 3.3 两个招呼语任务共用 id `打招呼`

**位置**：`handles.ts`、`delivery.ts`

```ts
tasks.customGreeting() // id: '打招呼', label: '自定义招呼语'
tasks.aiGreeting() // id: '打招呼', label: 'AI招呼语'
```

工作流以 `id` 为键构建 `taskMap` 和 `resolvedHandlers`：

- `taskMap` 中后定义的 AI 任务覆盖自定义任务
- `resolvedHandlers` 中后解析的 handler 覆盖先解析的
- 若只启用自定义招呼语，可能仍执行自定义 handler，但任务元数据（label/state/stateMsg）来自 AI 定义
- 若两者都启用，只发送 AI 版本

影响：日志/状态显示可能不准确；配置组合的行为不够直观。

### 3.4 `confRecommend` 与 `confDelete` 可能是空操作

**位置**：`src/composables/conf/index.ts`

```ts
function confRecommend() {
  deepmerge(formData, recommendedValues) // 返回值丢弃
  toast.add(...)
}

function confDelete() {
  deepmerge(formData, defaultFormData) // 返回值丢弃
  toast.add(...)
}
```

`deepmerge` 默认 `clone: true`：

```ts
const output = options.clone ? { ...target } : target
```

不接收返回值、也不传 `{ clone: false }`，意味着修改发生在一个临时副本上。

影响：

- “使用推荐配置”按钮可能只弹 Toast，不改变配置
- “清空配置”按钮可能只弹 Toast，不改变配置

对比 `confReload`、`confImport` 都显式传了 `{ clone: false }`，可以判断这是遗漏。

### 3.5 缓存模块未接入投递流程

**位置**：`src/composables/useApplying/index.ts`、`src/composables/usePipelineCache.ts`

- `cachePipelineResult` / `checkJobCache` 已导出
- `PipelineCacheManager` 已实现 TTL、LRU、存储
- 但 `boss/index.ts` 中读取缓存的代码被注释
- 投递流程没有调用 `cachePipelineResult`

影响：

- 配置里的“启用缓存/清空缓存”不会加速投递
- 清空缓存只会清空一个当前没人读的存储键

### 3.6 `stateMaps` 没有写入路径

**位置**：`useApplying/index.ts`

```ts
const stateMaps = ref(new Map<string, any>())
...
state: stateMaps.value.get(jobData.key) || {}
```

全项目没有 `stateMaps.value.set(...)`。因此：

- 每个职位每次执行的 `state` 都是新的 `{}`
- 高德任务写入的 `state.amap` 只在本次执行内有效
- 若未来需要跨轮次缓存状态，这个设计还没有闭环

### 3.7 构建错误只提示，不中止

**位置**：`useApplying/index.ts`

```ts
if (errMsg) {
  alert(`工作流构建错误, 请检查配置:\n${errMsg}`)
  errorMessage.value = errMsg
}
```

随后 `executeAll()`：

```ts
errorMessage.value = null
status.value = 'running'
```

影响：

- 用户看到一次 alert
- 出错的任务不会进入管线
- 投递仍会继续，可能表现为“AI 筛选没生效”“高德没生效”但不明显

### 3.8 配置迁移不累积

**位置**：`conf/index.ts` 的 `formDataHandler`

从最新版本倒序遍历，遇到 `from.version >= version` 就 break。非常老的配置只会执行最新一条迁移，中间的迁移被跳过。

影响：旧版本升级后，部分字段可能保持旧结构；目前靠 `deepmerge` 默认值和 `ChatModel` 的字符串 Prompt 兜底，但不保证所有字段都兼容。

### 3.9 模型 Provider 缓存导致配置修改不生效

**位置**：`useModel/chatModel.ts`

```ts
let provider = this.providers.get(model.model)
if (!provider) {
  provider = createOpenAI({ baseURL: conf.data?.base_url, apiKey: conf.data?.api_key })
}
this.providers.set(model.model, provider)
```

Provider 按模型 key 缓存。修改同一个模型的 `base_url`、`api_key` 后，已缓存的 Provider 不会更新。

影响：改完模型配置后直接开始投递，可能仍使用旧配置。建议刷新页面。

### 3.10 AI 超时单位与文案不一致

**位置**：`useModel/common.ts`、`chatModel.ts`

- 文案：`18000s / 30分钟`
- 默认值：`18000`
- 实际传给 AI SDK 的 `timeout` 按毫秒处理

影响：默认超时实际是 18 秒，不是 30 分钟。长 Prompt/慢模型容易超时。

### 3.11 `getBossData` 的 `encryptUserId` 传参可疑

**位置**：`entrypoints/boss/delivery.ts`

```ts
const bossData = await getBossData({
  securityId: rawData.jobitem.securityId,
  encryptUserId: ctx.helper.uid,
})
```

`ctx.helper.uid` 是当前登录用户的 `encryptUserId`；而 `getBossData` 请求体把该值作为 `bossId`：

```ts
body.append('bossId', job.encryptUserId)
```

如果接口期望的是 Boss 的加密 id，这里传错了对象，会导致：

- 返回当前用户自己的数据
- `sendMessage` 中的 `boss.data.bossId`、`bossSource`、`securityId` 不正确
- 招呼语发送失败或发错对象

这是一个**需要按接口实际语义确认**的疑点。若遇到“Boss信息获取”成功但消息发不出去，应优先排查这里。

### 3.12 工作内容正则未转义

**位置**：`handles.ts`

```ts
const re = new RegExp(`(?<!(不|无).{0,5})${x.toLowerCase()}(?!系统|软件|工具|服务)`)
```

用户输入会直接拼进正则。输入 `C++`、`(`、`[`、`\\` 等可能导致：

- `SyntaxError: Invalid regular expression`
- 任务抛错
- 该职位被标记为 `error`

建议对关键词做 `escapeRegExp`，或改用字符串包含 + 手工上下文判断。

### 3.13 薪资严格模式的帮助文案与代码方向相反

**位置**：`SalaryRange.vue` vs `useApplying/utils.ts`

- 文案：“目标薪资需完全在职位范围内”
- 代码：`min <= jobMin && jobMax <= max`，即**职位区间被目标区间包含**

按代码行为配置，避免被文案误导。

### 3.14 卡片按任务过滤可能不生效

**位置**：`JobCards.vue`

```ts
const res = helper.jobResultMaps.get(job.key)
if (!res || !res.id) return filterItemsChecked.value.not_started ?? true
if (res.status === 'success') ...
if (res.status === 'error') ...
if (filterItemsChecked.value[res.id] === false) return false
```

但工作流从未给 `TaskResult.id` 赋值（`execute` 只设置 `status`/`msg`/`reason`）。因此：

- 所有卡片都会落到 `not_started` 分支
- 按任务过滤的下拉项基本不会生效
- 只有“未开始”复选框实际影响显示

### 3.15 版本比较使用字符串

**位置**：`App.vue`

```ts
const isDot = computed(() => (helper.netConf.value?.version ?? '0') > VITE_VERSION)
```

字符串比较在 `0.5.9` vs `0.5.10` 时会得到错误结果。发版时应保持版本号位数一致，或改用 semver 比较。

### 3.16 `responses` 与高级开关对投递无效

**位置**：`useModel/chatModel.ts`、`useModel/openai.ts`

- `openai.createModel()` 支持 `responses` 开关，但只被模型测试使用
- 投递中的 `ChatModel.createAgent()` 固定使用 `provider.chat(...)`
- `advanced.json` / `advanced.stream` 也没有在 `createAgent` 中读取

影响：

- 勾选“Responses API”不会改变 AI 筛选/招呼语的请求方式
- 高级配置里的 JSON/流式开关对投递流程没有作用

## 4. 维护风险

### 4.1 对目标站点的强依赖

| 依赖                                    | 风险                            |
| --------------------------------------- | ------------------------------- |
| Vue 2 `__vue__`                         | 升级 Vue 3 或移除暴露后整体失效 |
| 硬编码 CSS 选择器                       | 改版即失效                      |
| 页面 data 字段名                        | 压缩/重命名后失效               |
| `window._PAGE` / `Cookie.get`           | 登录态实现变化后失效            |
| `friend/add.json`、`getBossData` 等接口 | 参数/返回结构变化后失效         |
| MQTT `chatws`、`wt`、protobuf           | 协议升级后失效                  |

### 4.2 缺少测试

- 没有单元测试，`rangeMatch`、`parseFiltering`、`renderTemplate` 这类纯函数完全可以单测
- 没有 E2E，工作流/筛选/消息只能手工验证
- 没有 CI 类型检查（当前 workflow 只构建打包）

### 4.3 子模块耦合

`devlog-ui` 是子模块，CI/本地都必须递归 checkout。子模块不可用会直接阻断构建。

### 4.4 依赖升级风险

- AI SDK 7 的 API 仍在演进（`ToolLoopAgent`、`Output`、`toUIMessageStream`）
- shadcn-vue / Reka UI 的组件 props 与本地 `src/components/ui` 实现可能变化
- WXT 0.21 的 `injectScript`、manifest 行为可能变化
- `protobufjs`、`mqtt` 升级可能影响消息编码

### 4.5 性能与资源

- 职位卡片 + Shadow DOM + 大量 `UBadge` 在长列表下可能卡顿
- 图片通过 `number[]` 跨上下文传输，大图会产生明显拷贝
- `sync` 存储不适合大对象
- AI 请求串行，整体速度受模型延迟限制
- 日志最多 1000 条，sessionStorage 最多 500 条，长跑会占用内存

## 5. 改进建议（按优先级）

### P0：影响核心功能

1. **修正去重键**：相同公司用 `encryptBrandId`，相同 HR 用 `encryptBossId`，并在 `JobData` 中补充 `brandId`/`bossId` 字段
2. **修正招呼语任务 id**：`customGreeting` 与 `aiGreeting` 使用不同 id，明确优先级
3. **确认 `getBossData` 的 bossId**：如果确实传错，修复后招呼语才能稳定
4. **给 `JobData` 回填 `isFriend`**：使用 `detail.relationInfo.beFriend`
5. **修复 `confRecommend`/`confDelete`**：传 `{ clone: false }` 或接收返回值后 `Object.assign`

### P1：影响体验/可维护性

6. **接入或移除缓存**：当前“启用缓存”是误导
7. **模型 Provider 失效**：编辑模型后清理 `providers` 缓存
8. **统一超时单位**：把文案改成毫秒，或把默认值改成 1800000
9. **关键词正则转义**
10. **修复卡片按任务过滤**：在 `execute` 中写入 `res.id = t.id`
11. **工作流构建错误中止**：`executeAll` 开始前检查 `errorMessage`
12. **`stateMaps` 闭环**：写入/读取/清理策略
13. **移除死代码**：options 占位、未引用 SDK、`request.ts`、`getJobDetail`

### P2：工程质量

14. 为纯函数补单测：`rangeMatch`、`parseFiltering`、`renderTemplate`、`saveSet/loadSet`
15. 修复现有类型错误后，CI 增加 `npm run check` 与 `npm run lint`
16. 版本比较改用 semver
17. 引入站点结构预检：找不到 `#wrap.__vue__` 时给出明确提示，而不是等 20 秒
18. 为 `stop()` 增加 `AbortController`，真正中断详情/AI 请求
19. 拆分 Provider 抽象，支持非 OpenAI 协议
20. UI 文案 i18n 化

## 6. 使用建议（降低风险）

如果只是个人求职使用：

- 把 `deliveryLimit` 设在 80~120，不要贴近 150
- 增大 `delayDeliveryInterval`（例如 8~15 秒）和 `delayDeliveryPageNext`
- 不要同时开启过多筛选 + AI，先小批量验证
- 先用“模型测试”确认 AI 可用，再开启 AI 筛选/招呼
- 不要使用来源不明的中转 API；不要把 Key 提交到仓库
- 遇到“操作频繁”立即停止，不要连续重试
- 关注 Boss 页面改版；扩展失效时先检查选择器与 `__vue__`
- 定期导出配置；预设切换前先保存

## 7. 结论

boss-helper-plus 的架构是清晰的：

- 用 Shadow DOM 做 UI 隔离
- 用页面 Vue 实例做数据桥接
- 用任务管线做可插拔筛选
- 用 comctx 做三层通信
- 用 MQTT + protobuf 做聊天发送

它的主要风险不在“代码写得多差”，而在于：

1. **强依赖目标站点的内部实现**，随时可能失效
2. **自动化行为本身的风控与合规风险**
3. **若干实现细节与命名/文案不一致**，会误导配置与排障

上面的 P0 问题修复后，核心投递链路的可预期性会明显提升；P1/P2 更多是工程质量与长期维护问题。
