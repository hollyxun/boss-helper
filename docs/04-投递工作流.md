# 04 · 投递工作流

本文是整个项目最核心的部分：职位如何从页面列表进入管线，经过哪些筛选，什么情况下会被跳过，什么时候真正投递，以及失败后如何记录。

涉及文件：

- `src/composables/useApplying/type.ts`：任务与结果的类型、任务定义辅助函数、懒加载 Proxy
- `src/composables/useApplying/index.ts`：管线构建、执行、停止、统计
- `src/composables/useApplying/handles.ts`：`TaskRegistry`，所有筛选与招呼任务
- `src/composables/useApplying/utils.ts`：范围匹配、AI 结果解析、集合持久化
- `src/entrypoints/boss/delivery.ts`：Boss 站点的任务编排

## 1. 任务模型

### 1.1 一个任务长什么样

```ts
type Task<C, T, S> = {
  id: string
  task: TaskHandler<C, T, S>
  deps: string[]
  before: Handler<C, T, S>[]
  after: Handler<C, T, S>[]
  label?: string
  desc?: string
  state?: JobStatus
  stateMsg?: string
  onEnd?: (ctx: TaskContext<C, T, S>) => void | Promise<void>
}
```

`task` 是**两阶段**的：

1. **构建期**：`await task.task(ctx)` 返回 `undefined` 或一个 `Handler`
2. **执行期**：对每个职位调用这个 `Handler(ctx, data)`

`Handler` 的返回值：

```ts
type Handler = (ctx, data) => Promise<void | TaskResult | Array<TaskResult | void>>
```

`TaskResult`：

```ts
type TaskResult = {
  isSkip?: boolean // 是否终止该职位的后续任务
  reason?: string // 详细原因（写入日志/悬浮提示）
  status?: JobStatus // 结果状态
  msg?: string // 卡片上显示的短文本
  isCache?: boolean
  id?: string
}
```

### 1.2 定义任务的辅助函数

```ts
const myTask = defineTaskHandler(
  '任务ID',
  (ctx) => {
    if (!ctx.helper.conf.formData.someSwitch.value) return
    return async (ctx, data) => {
      if (shouldSkip(data)) {
        return taskResult.skip('原因')
      }
    }
  },
  {
    label: 'UI 标签',
    deps: ['另一个任务ID'],
    state: 'ai',
    stateMsg: 'AI处理中',
  },
)
```

`defineTaskHandler` 支持在调用时覆盖 `task`、`deps`、`before`、`after`、`label`、`state` 等，因此同一个 `TaskRegistry` 方法可以按不同依赖复用。例如：

```ts
tasks.activityFilter({ deps: ['岗位详情获取'] })
```

### 1.3 任务结果构造器

```ts
taskResult.skip(reason, (status = 'warn')) // 过滤，默认警告
taskResult.error(reason) // 过滤，状态 error
```

返回 `{ isSkip: true, reason, status }`。`status` 会影响卡片颜色、统计和下一轮是否重试。

## 2. 构建阶段：从任务定义到可执行管线

`executeAll()` 的第一步是 `await rebuild()`。`rebuild()` 做了五件事。

### 2.1 展开任务定义

```ts
const rawTasks = items.flatMap((i) =>
  typeof i === 'function' ? { ...i() } : Array.isArray(i) ? i : { ...i },
)
```

当前 `bossWorkflow` 传入的基本都是 `Task` 对象，所以这一步主要是浅拷贝。

### 2.2 逐个解析任务

```ts
for (const task of rawTasks) {
  taskMap.set(task.id, task)
  const result = await task.task(_ctx)
  if (!result) continue
  requiredIds.add(task.id)
  task.deps.forEach((d) => requiredIds.add(d))
  if (typeof result === 'function') {
    _resolvedHandlers.set(task.id, result)
  } else {
    _resolvedHandlers.set(task.id, result.fn)
    if (result.before) task.before.push(...result.before)
    if (result.after) task.after.push(...result.after)
  }
}
```

关键点：

- **配置是在构建期读取的**。`task.task(ctx)` 里的 `if (!conf.xxx.enable) return` 决定了任务是否进入本轮管线。
- 未启用的任务不会加入 `requiredIds`，因此默认被排除。
- 如果某个已启用任务依赖它，依赖 id 会被加入 `requiredIds`，即使该依赖任务未启用也会被排进管线（但执行时没有 handler，等于空操作）。这是一个容易踩的坑。
- 解析时抛出的异常会被捕获，记录到 `errors`，并注册一个“一执行就抛原异常”的 handler；该任务不会被加入 `requiredIds`。

### 2.3 依赖拓扑排序

```ts
const sort = (id) => {
  if (stack.has(id)) throw new Error(`Cycle: ${id}`)
  if (visited.has(id)) return
  const t = taskMap.get(id)
  if (!t || !requiredIds.has(id)) return
  stack.add(id)
  t.deps.forEach(sort)
  stack.delete(id)
  visited.add(id)
  _pipeline.push(t)
}
Array.from(requiredIds).forEach(sort)
```

- 深度优先，先依赖后自身
- 用 `stack` 检测环
- 用 `visited` 去重
- **相同 id 只保留一个任务**，实际保留的是 `taskMap.get(id)`，即最后一次出现的定义（见“重复 id”问题）

排序结果写入 `pipeline.value`；`resolvedHandlers` 是 `Map<id, Handler>`，执行时按 id 取。

### 2.4 生成节点状态（用于调试/UI）

`nodes` 中每个任务的状态：

| 状态              | 含义                                     |
| ----------------- | ---------------------------------------- |
| `active`          | 已解析出 handler，会执行                 |
| `dependency_only` | 只作为别人的依赖被加入，自己没有 handler |
| `shadowed`        | 同 id 的早期定义被后面的定义覆盖         |
| `failed`          | 构建期抛错                               |
| `disabled`        | 未启用且不需要作为依赖                   |
| `skipped`         | 预留状态，当前构建流程未使用             |

### 2.5 构建错误处理

如果 `errors` 非空：

```ts
logger.error('工作流构建错误, 请检查配置:', errMsg)
alert(`工作流构建错误, 请检查配置:\n${errMsg}`)
errorMessage.value = errMsg
```

注意：`executeAll()` 随后会把 `errorMessage.value = null`，并且**不会因为构建错误中止**。实际效果是：用户看到一次 `alert`，管线继续执行剩余任务。例如 AI 已启用但未选择模型，`HelperConfigError` 会让 AI 任务被排除，投递仍会继续。这一点在使用时需要留意。

## 3. 执行阶段：`executeAll`

### 3.1 主循环（简化伪代码）

```ts
await rebuild()
status.value = 'running'

while (status.value === 'running') {
  if (jobList.length === 0) {
    stepMsg = '没有职位可投递'
    break
  }

  // 1. 把没有结果的职位标记为等待；success/warn 保持不动
  for (const job of jobList) {
    const r = jobResultMaps.get(job.key)
    if (!r) jobResultMaps.set(job.key, { status: 'wait', msg: '等待中' })
    else if (r.status !== 'success' && r.status !== 'warn') {
      r.status = 'wait'; r.msg = '等待中'
    }
  }

  // 2. 开始前延迟
  await delay(delayDeliveryStarts, isStop)

  // 3. 逐个职位执行
  for (const [index, job] of jobList.entries()) {
    if (isStop()) break
    if (result.status === 'success' || result.status === 'warn') continue

    const data = { jobData: job, rawData: rawDataMap.get(job.key)!, state: ... }
    helper.jobMaps.set(job.key, data)
    helper.currentJob.value = job.key

    await execute(data, index)

    if (statistics.todayData.success >= deliveryLimit) {
      stepMsg = '投递达到数量限制'
      status.value = 'stop'
      break
    }
    await delay(delayDeliveryInterval, isStop)
  }

  if (isStop()) break

  // 4. 翻页
  const hasMore = await helper.loadMoreJob(delay(delayDeliveryPageNext, isStop))
  if (!hasMore) {
    status.value = 'stop'
    stepMsg = '投递结束, 无法继续下一页'
    break
  }
}
```

### 3.2 为什么 `success` / `warn` 会被跳过

`jobResultMaps` 保存每个职位在当前页面会话中的结果：

- `success`：已成功投递
- `warn`：被过滤/跳过
- `error`：执行失败
- 其它：等待/处理中

下一轮（例如用户暂停后继续）只会重试 `error` 和未完成的职位；`success` 与 `warn` 直接跳过。若希望重新处理被过滤的职位，点击“重置筛选”（`helper.reset()`），它会把所有非 `success` 的状态改回 `wait`。

### 3.3 结束与通知

`finally` 中：

```ts
if (!stepMsg) {
  stepMsg = '投递结束'
  status.value = 'pending'
} else if (status.value !== 'stop') {
  status.value = 'error'
  errorMessage.value = stepMsg
}
void helper.notification(stepMsg)

for (const t of pipeline.value) {
  await t.onEnd?.({ now, helper, index: 0, log })
}
```

- 正常跑完（理论上较少见，因为通常会因“无法翻页”结束）：状态回到 `pending`
- 达到投递上限/无法翻页/用户停止：状态 `stop`
- 未知异常：状态 `error`
- 无论哪种，都会发通知（页面不可见时发系统通知）
- 所有任务的 `onEnd` 会被调用，用于把内存中的集合落盘（相同公司/HR）

### 3.4 停止与重置

```ts
const stop = () => (status.value = 'stop')
const reset = () => {
  status.value = 'pending'
  for (const job of jobList) {
    const v = jobResultMaps.get(job.key)
    if (!v || v.status === 'success') continue
    v.msg = '等待中'
    v.status = 'wait'
  }
}
```

停止是**协作式**的：只在任务之间、延迟中、翻页前检查，不会中断正在进行的 `fetch`。如果正在等一个 60 秒的详情或一个 AI 请求，需要等它返回。

## 4. 单职位执行：`execute`

```ts
const execute = async (data, index = 0) => {
  statistics.todayData.total++

  try {
    let skipPipeline = false
    let errorLog = false

    for (const t of pipeline.value) {
      if (isStop()) break
      jobResultMaps.set(data.jobData.key, {
        status: t.state || 'running',
        msg: t.stateMsg || '运行中',
      })

      const res = await executeTask(t, data, index, log)

      if (res != null) {
        res.msg ??= t.label ?? t.id
        res.status ??= res.isSkip ? 'warn' : undefined
        if (res.isSkip) {
          skipPipeline = true
          break
        }
      }
    }

    if (!skipPipeline) {
      jobResultMaps.set(key, { status: 'success', msg: '投递成功' })
      statistics.todayData.success++
    }
  } catch (e) {
    // 任务抛错已在 executeTask 内被包装为 isSkip + error；这里只处理更外层异常
    status.value = 'error'
    throw e
  }
}
```

每个任务执行后，`finally` 块还会：

- 把结果合并进 `jobResultMaps`
- 按任务 id 和结果状态累加 `statistics.todayData.tasks[t.id][status]++`

因此统计面板不仅能看“成功多少”，还能看“每个任务过滤了多少”。

### 4.1 结果合并规则

`meginResults`（源码中的拼写）负责把多个结果合并成一个：

- `isSkip` 取或
- `reason` / `msg` 用换行拼接
- `isCache` 取或
- `status` 取 `jobStatusList` 中**索引更大**的那个

`jobStatusList` 的顺序：

```ts
;['pending', 'wait', 'running', 'request', 'ai', 'success', 'warn', 'error']
```

所以 `error` 会覆盖 `warn`，`warn` 会覆盖 `success`。这用于把“多个子检查的结果”合并成最终状态。

### 4.2 `executeTask` 的钩子顺序

```ts
const fns = [...task.before, handler, ...task.after]

for (const fn of fns) {
  res = meginResults(await fn(ctx, data))
  if (res?.isSkip || isStop()) break
}
```

- `before` 先执行
- 主 handler 其次
- `after` 最后
- 任意一步返回 `isSkip` 就停止
- 任意一步抛 `DependencyMissingError` 时，会先执行对应依赖任务，再重试当前函数

### 4.3 依赖缺失的自动补执行

```ts
if (e instanceof DependencyMissingError) {
  const dep = resolvedHandlers.get(e.taskId)
  if (dep) {
    await dep(ctx, data)
    res = meginResults(await fn(ctx, data))
    continue
  }
}
throw e
```

这是配合 `createLazyObject` 的兜底：当筛选任务访问 `data.rawData.detail.xxx` 而详情还没取时，会先执行 `岗位详情获取`。

## 6. 筛选语义

### 6.1 岗位名 / 公司名

```ts
// 岗位名大小写不敏感
const text = data.jobName.toLowerCase()
for (const x of keywords) {
  if (text.includes(x.toLowerCase())) {
    return form.include ? undefined : taskResult.skip(`岗位名含有排除关键词 [${x}]`)
  }
}
if (form.include) return taskResult.skip('岗位名不包含关键词')
```

- `include = true`：白名单，命中任意关键词通过
- `include = false`：黑名单，命中任意关键词跳过
- 公司名使用 `text.includes(x)`，**区分大小写**

### 6.2 工作内容

```ts
const re = new RegExp(`(?<!(不|无).{0,5})${x.toLowerCase()}(?!系统|软件|工具|服务)`)
```

- 大小写不敏感（两边都转小写）
- 负向后行断言：关键词前 0~5 个字符内出现“不/无”时不算命中，减少“不是外包”“无需销售”误判
- 负向前瞻：关键词后紧跟“系统/软件/工具/服务”时不算命中，减少“销售系统”“测试工具”误判
- 关键词直接拼进正则，**未转义**；如果用户输入 `(`、`[` 等字符，会构造非法或意外正则，任务会抛错

### 6.3 HR 职位

```ts
if (content.trim() === x) { ... }
```

- 精确相等，不是包含
- 默认选项：`经理`、`主管`、`法人`、`人力资源主管`、`hr`、`招聘专员`
- `include = true` 为白名单；`false` 为黑名单
- 用户可手动输入新选项（`FormSelect` 支持创建）

### 6.4 工作地址

```ts
if (!keywords.length || !jobData.address) return
const content = jobData.address.toLowerCase()
for (const x of keywords) {
  if (content.includes(x.toLowerCase())) return
}
return taskResult.skip(`工作地址不包含关键词: ${content}`)
```

- 只有“包含”模式，没有排除模式；配置里的 `include` 被强制为 `true`（迁移时也会覆盖）
- 关键词为空或地址为空时直接通过

### 6.5 薪资范围

薪资按单位分组匹配：

```ts
const arr = [
  ['元/时', advancedValue.H],
  ['元/天', advancedValue.D],
  ['元/月', advancedValue.M],
  ['K', value],
]
for (const [unit, range] of arr) {
  if (text.includes(unit) && !rangeMatch(text, range)) {
    return taskResult.skip(...)
  }
}
```

`rangeMatch(rangeStr, [min, max, mode])` 的规则：

| 模式                   | 公式                                   | 含义                                   |
| ---------------------- | -------------------------------------- | -------------------------------------- |
| 严格（`mode = true`）  | `min <= jobMin && jobMax <= max`       | 职位薪资区间必须**完全落在**目标区间内 |
| 宽松（`mode = false`） | `max(jobMin, min) <= min(jobMax, max)` | 两个区间有任意重叠                     |

> 注意：`SalaryRange.vue` 的帮助文案写的是“目标薪资需完全在职位范围内”，与代码公式的方向相反。以代码为准：**严格 = 职位区间被目标区间包含**。这一点在配置薪资筛选时容易误解。

`rangeMatch` 只取字符串中的第一段数字/数字区间，忽略“13 薪”“·14薪”等后缀。例如 `8-13K·13薪` 解析为 `8-13`。

`advancedValue` 的 H/D/M 默认都是 `[0, 1, false]`。一旦启用薪资筛选，遇到“元/时”“元/天”“元/月”的职位就会用这些默认值匹配，可能被大量过滤。启用薪资筛选时，应同时检查高级配置中的三种单位。

### 6.6 公司规模

```ts
if (!rangeMatch(text, companySizeRange.value)) {
  return taskResult.skip(...)
}
```

- 解析 `brand.scale` 中的第一段数字，如 `500-999人`
- 默认 `[500, 2000, true]`，严格模式
- 严格模式下，“500-999人”通过；“1000-9999人”不通过（因为 9999 > 2000）

### 6.7 活跃度

```ts
if (!activeText && !activeTime) skip('无活跃内容...')
else if (!activeText && activeTime && now - activeTime >= 7天) skip(...)
else if (!activeText) skip(...)
else if (activeText.includes('月') || activeText.includes('年')) skip(...)
```

- 列表项的 `lastModifyTime` 会被转成 `activeTimeStr`（今日/昨日/本周/本月/较久未活跃）
- 有“月/年”字样视为不活跃
- 只有时间戳且超过 7 天视为不活跃
- 两者都没有则跳过

### 6.8 猎头 / 金牌面试官 / 已沟通 / 好友

| 过滤器     | 判断                                            | 说明                                                     |
| ---------- | ----------------------------------------------- | -------------------------------------------------------- |
| 猎头       | `boss.isHeadhunter === true`                    | 来自列表项 `goldHunter === 1`                            |
| 金牌面试官 | `detail.bossInfo.avatarStickerUrl` 包含固定哈希 | 用头像贴纸判断                                           |
| 已沟通     | `rawData.jobitem.contact`                       | 列表接口返回的字段                                       |
| 好友状态   | `jobData.boss.isFriend === true`                | 当前代码没有回填该字段，实际很难触发；主要靠“已沟通”兜底 |

### 6.9 相同公司 / 相同 HR

设计意图：

- `local:sameCompany` 存公司键
- `local:sameHr` 存 HR 键
- 每个 uid 一个 Map，值为时间戳
- 每投递 3 个保存一次，轮次结束 `onEnd` 再保存
- `expire` 可配置 7/30/90/180/360 天，`saveSet` 时 GC

实际实现：

```ts
if (someSet.has(data.key)) skip('相同公司已投递')
...
someSet.set(data.key, Date.now())
```

`data.key` 来自 `JobData.key`，而转换函数是：

```ts
const key = `boss::${item.encryptJobId}`
```

也就是说两个过滤器都用**职位 id** 作为键，而不是 `encryptBrandId` 或 `encryptBossId`。同一职位不会在同一轮重复出现，因此这两个过滤器几乎不会命中；它们并没有实现“跨岗位的公司/HR 去重”。详见 [11-已知限制与风险.md](./11-已知限制与风险.md#3-代码层面的已知问题)。

### 6.10 高德地图

```ts
state.amap.geocode = await amapGeocode(jobData.address)
state.amap.distance = await amapDistance(state.amap.geocode.location)
```

- 先地理编码得到经纬度
- 再并发请求三种距离：直线（type=0）、驾车（type=1）、步行（type=3）
- 每个阈值 `> 0` 才生效：
  - 直线距离：km，比较 `amap.distance > straightDistance * 1000`
  - 驾车：km + 分钟
  - 步行：km + 分钟
- 任一超标返回 `skip`
- 高德未初始化/接口失败返回 `skip('高德地图未初始化')` 或 `skip('api数据异常')`

### 6.11 AI 过滤

```ts
const content = await chatModel.chat('filtering', data).then((r) => r.text)
const { message, rating } = parseFiltering(content)
const threshold = aiFiltering.score ?? 10
if (rating < threshold) {
  return taskResult.skip(`${message || 'AI 评分不达标'}（AI 评分 ${rating}，低于 ${threshold}）`)
}
```

`parseFiltering`：

- 把 `positive` 与 `negative` 中的 `score` 取绝对值后分别求和
- `rating = positive - negative`
- `message` 拼接分数与正负理由
- 解析失败时 `res` 为 `null`，两个和都是 0，`rating = 0`，通常会被过滤

默认 `score = 10`，即正负抵消后至少 +10 分才通过。

被过滤时 `execute()` 会写一条「投递」日志，标签为 `AI 过滤`、原因里带评分；同时 `chatModel` 会写一条「AI 调用」日志，含完整提示词与回复，方便回看为什么没通过。

### 6.12 自定义招呼语

```ts
let msg = customGreeting.value
if (greetingVariable.value) {
  msg = Array.isArray(msg)
    ? msg.map((item) =>
        item.type === 'text' ? { ...item, content: renderTemplate(item.content, data) } : item,
      )
    : renderTemplate(msg, data)
}
await ctx.helper.sendMessage?.(data, msg)
```

- 支持字符串或 `CustomGreetingItem[]`（文本 + 图片）
- `greetingVariable` 开启时用 `{{ jobData.xxx }}` 渲染
- 图片消息的 `image` 是 IndexedDB 中的 key（`img-<md5>`），发送前由 background 取出、上传到 Boss、再构造 protobuf
- 文本消息发送前会等待 `delayMessageSending`，并把内容写入 `helper.pendingMessages`，让用户在聊天框中手动修改/发送

### 6.13 AI 招呼语

```ts
const msg = await chatModel.chat('greetings', data).then((r) => r.text)
await ctx.helper.sendMessage?.(data, msg)
```

- 不走变量渲染（Prompt 中的 `{{ }}` 在 `ChatModel.chat` 内统一渲染）
- 直接发送模型输出的文本
- 如果自定义招呼语也启用，二者共用 id，实际只会有一种生效（见已知问题）

## 7. 统计与缓存

### 7.1 统计

`useStatistics()` 维护：

```ts
type Statistics = {
  date: string
  success: number
  total: number
  repeat: number
  activityFilter: number
  tasks: { [taskId: string]: { [status: string]: number } }
}
```

- `total`：每次 `execute()` 自增，即“扫描过的职位数”（重复扫描会重复计数）
- `success`：完整通过管线并投递成功
- `repeat`：相同公司/HR 命中时自增（当前键问题导致很少触发）
- `activityFilter`：活跃度过滤命中
- `tasks`：每个任务各状态计数
- `todayData` 通过 `watchThrottled`（200ms，deep）自动写 `local:web-geek-job-Today`
- `updateStatistics()` 在统计面板挂载时调用：
  - 读取历史数组 `local:web-geek-job-Statistics`
  - 如果今天的记录日期一致，合并；否则把旧记录前置到历史数组，再写新的一天

注意：`total`、`success` 是页面会话内的内存值，刷新页面后需要 `updateStatistics()` 才能恢复当天数据。统计面板的数值是“脚本估算”，不是 Boss 官方计数。

### 7.2 缓存

`usePipelineCache.ts` 定义了一个完整的缓存管理器：

- key：`encryptJobId`
- 字段：职位名、公司名、状态、消息、过期时间、创建/访问时间、命中次数、处理器类型
- TTL：AI 7 天、高德 5 天、基础 3 天（按消息内容推断类型）
- 清理：每 6 小时清理过期；超过 `maxCacheSize`（默认 10000）按 LRU 淘汰
- 存储：`local:pipeline-cache`

0.0.2 起已接入投递流程：

- `executeAll` 逐岗位处理前，若 `formData.useCache.value` 为真，先 `checkJobCache(job.key)`；
- 命中则把 `jobResultMaps` 设成缓存里的状态并跳过该岗位，日志里记一条「缓存命中」，原因写上次处理时间；
- `execute()` 的 `finally` 里对非 `error` 结果调用 `cachePipelineResult(...)` 写回，所以「启用缓存」现在会真正跳过处理过的岗位；
- 命中缓存的岗位不会重复计入当日成功数；「清空缓存」按钮会清掉全部记录。

> 注意：缓存只按 `encryptJobId` 记录，不区分筛选规则。改了配置想重跑，需要先清空缓存。

## 8. 如何新增一个过滤任务

以“排除标题含‘实习’的职位”为例：

1. **加配置类型**（`src/types/formData.ts`）：
   ```ts
   internFilter: FormDataCheckbox
   ```
2. **加默认值**（`src/composables/conf/info.ts`）：
   ```ts
   internFilter: { value: false },
   ```
3. **加任务**（`src/composables/useApplying/handles.ts` 的 `TaskRegistry`）：
   ```ts
   internFilter = defineTaskHandler<C, T, S>('实习过滤', (ctx) => {
     if (!ctx.helper.conf.formData.internFilter.value) return
     return async (_, { jobData }) => {
       if (jobData.jobName.includes('实习')) {
         return taskResult.skip('实习职位')
       }
     }
   })
   ```
4. **加入编排**（`src/entrypoints/boss/delivery.ts`）：
   ```ts
   tasks.internFilter(),
   ```
5. **加入配置 UI**（`src/entrypoints/boss/index.ts` 的 `getConfigItems()`）：
   ```ts
   { type: 'checkbox', key: 'internFilter' }
   ```
6. 在 `formInfoData` 中补 `label` / `data-help`，否则 UI 显示为空。

注意：

- 任务 id 必须全局唯一（当前 `打招呼` 就是反例）。
- 如果任务依赖详情，声明 `{ deps: ['岗位详情获取'] }`。
- 配置读取发生在构建期；运行中改配置不会热更新，需要停止后重新开始（`executeAll` 会重新 `rebuild`）。
- 新任务的结果会自动进入统计和卡片状态，无需额外接线。

## 9. 工作流相关坑位清单

| 坑                 | 说明                                                                                             |
| ------------------ | ------------------------------------------------------------------------------------------------ |
| 配置只在构建期读取 | 运行中改配置不生效；暂停→继续会重新构建，但已处理职位的成功/警告状态会保留                       |
| 依赖任务被禁用     | 依赖 id 仍会进入管线，但没有 handler，可能表现为“依赖步骤什么都没做”                             |
| 重复任务 id        | 后定义覆盖先定义；`打招呼` 是实际案例                                                            |
| `after` 钩子       | 只有 handler 没有返回 `isSkip` 时才会继续执行 `after`；抛错会跳过                                |
| 抛错 = 跳过        | 任务抛异常会被包装成 `error` 并终止该职位管线，不会重试                                          |
| `state` 不持久     | `stateMaps` 没有写入路径，每次 `execute` 的 `state` 都是空对象；高德结果只在本职位本次执行内有效 |
| AI 解析失败        | `rating` 为 0，默认会被过滤，而不是“放行”                                                        |
| 统计不是官方数据   | `total/success` 是脚本计数，刷新/多标签页可能不一致                                              |
| 缓存不区分规则     | 缓存按岗位记录，改筛选/提示词后要手动「清空缓存」才会重跑                                        |
